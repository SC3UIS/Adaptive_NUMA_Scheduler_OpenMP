# Adaptive NUMA Scheduler - Operational Guide

## 1. Introduction

This document describes the internal operation of the adaptive NUMA scheduler implemented using OpenMP Tools (OMPT), Linux Performance Counters (`perf_event_open`), and the hwloc library. The primary objective of the system is to detect remote memory access behavior in NUMA architectures and dynamically react by migrating threads to more appropriate NUMA nodes, reducing memory access latency and improving the overall performance of parallel applications.

## 2. General Architecture

The scheduler is composed of four major subsystems that work together throughout the execution of the application. The first subsystem is the OMPT integration layer, which intercepts events generated by the OpenMP runtime. The second subsystem is the hardware monitoring infrastructure based on `perf_event_open`, responsible for collecting execution metrics for each thread. The third subsystem is the decision engine, which analyzes the collected metrics and determines whether migration could improve performance. Finally, the fourth subsystem is the NUMA migration engine implemented using hwloc, which changes thread affinity and relocates threads between NUMA nodes when necessary.

## 3. Execution Flow

When the application starts, the OpenMP runtime loads the tool through the `OMP_TOOL_LIBRARIES` environment variable. OMPT then invokes the `ompt_start_tool` function, which registers the scheduler initialization and finalization routines. During initialization, the scheduler discovers the system NUMA topology, registers all required callbacks, and launches a dedicated monitoring thread. From that point onward, every OpenMP thread created by the runtime is registered by the tool and associated with its own hardware performance counters. Once measurements begin, the scheduler continuously collects metrics and evaluates migration opportunities throughout the execution.

## 4. NUMA Topology Discovery

NUMA topology discovery is performed during initialization using the hwloc library. The scheduler identifies all available NUMA nodes and stores the CPU sets associated with each node. This information allows the tool to determine where each thread is currently executing and provides the affinity masks required to perform controlled migrations between NUMA domains.

## 5. Thread Management

All thread-related information is stored inside the `ThreadInfo` structure. Each entry contains OMPT and Linux identifiers, processor location, NUMA node assignment, measurement state, migration metadata, and references to hardware performance counters. This structure acts as the scheduler's internal database and enables continuous tracking of every thread throughout the lifetime of the application.

## 6. Performance Monitoring

The scheduler uses hardware performance counters to observe memory behavior and computational efficiency for each thread. The monitored events include remote cache fills (`0xD044`), retired instructions, CPU cycles, and total cache fills (`0xFF44`). These metrics are collected independently for every thread and later analyzed by the decision engine to determine whether migration may be beneficial.

## 7. Measurement Windows

Performance data is collected by a dedicated monitoring thread that wakes up every 100 milliseconds. During each observation window, the scheduler reads the current values of all hardware counters and computes differences relative to the previous window. This delta-based approach focuses on recent behavior and avoids relying on cumulative values collected since the beginning of execution.

## 8. Derived Metrics

Several useful metrics are derived from the collected hardware counters. The scheduler computes the number of remote accesses, executed instructions, consumed CPU cycles, and total cache fills observed during each monitoring window. Using these values, it calculates IPC (Instructions Per Cycle), which reflects computational efficiency, and the remote access ratio, which indicates the fraction of cache fills originating from memory located in a remote NUMA node.

## 9. Adaptive Threshold Learning

Instead of relying on a fixed migration threshold, the scheduler implements an adaptive learning phase. During the first nine monitoring windows, remote access ratios are accumulated and used to characterize the normal behavior of each thread. During the tenth window, the scheduler computes the average ratio observed so far and stores it as a baseline reference. This adaptive threshold is subsequently used to identify abnormal memory access behavior.

## 10. Decision Engine

After the adaptive threshold has been established, the scheduler continuously compares the current remote access ratio against the learned baseline. If the observed ratio exceeds the threshold and the thread is not currently under cooldown protection, the scheduler marks that thread as a migration candidate. Rather than migrating immediately, the system creates a pending migration request that will be executed later at a safe synchronization point provided by the OpenMP runtime.

## 11. Migration Strategy

Thread migrations are performed through the `migrate_to_opposite_node` function. The implemented strategy is intentionally simple: a thread executing on NUMA node 0 is moved to node 1, while a thread executing on node 1 is moved to node 0. Affinity is updated using `hwloc_set_thread_cpubind`, ensuring that only the selected thread is affected. This approach minimizes migration overhead and avoids interfering with the execution of other threads.

## 12. Ping-Pong Prevention

One common issue in adaptive scheduling systems is the possibility of threads repeatedly migrating back and forth between NUMA nodes without achieving measurable benefits. To prevent this behavior, the scheduler introduces a cooldown mechanism. After each migration, a thread must wait for a predefined number of monitoring windows before becoming eligible for another migration. This stabilization period reduces oscillations and limits unnecessary migration overhead.

## 13. OMPT Integration

The scheduler relies on multiple OMPT callbacks to integrate with the OpenMP runtime. Thread creation and termination events are used to allocate and release resources. Parallel region callbacks provide execution context and runtime information. Additionally, implicit task callbacks serve as safe synchronization points where pending migrations can be applied without disrupting the execution model of the OpenMP runtime.

## 14. Monitoring Thread

The monitoring thread serves as the operational core of the scheduler. Its primary responsibility is to periodically wake up, read hardware performance counters, calculate derived metrics, update adaptive thresholds, and determine whether migration conditions have been met. All observation and analysis logic is concentrated within this component, while actual migrations are delegated to OMPT callbacks executed by the runtime.

## 15. Finalization and Resource Cleanup

When the application terminates, OMPT invokes the `ompt_finalize` routine. During this stage, the monitoring thread is stopped in a controlled manner and joined with the main process. The scheduler then disables and closes all hardware performance counters, prints a final summary of thread activity, and releases all hwloc structures associated with the NUMA topology. This guarantees proper cleanup of all allocated resources.

## 16. Configurable Parameters

The scheduler behavior can be adjusted through several constants defined at the beginning of the source code. The most important parameters include the monitoring period (`MONITOR_MS`), the maximum number of supported threads (`MAX_THREADS`), the maximum number of NUMA nodes considered (`MAX_NUMA_NODES`), and the cooldown duration (`COOLDOWN_WINDOWS`). These values can be tuned to accommodate different hardware configurations and application workloads.

## 17. Main Function Reference

The `ompt_start_tool` function acts as the entry point of the tool and provides the initialization and finalization callbacks to the OpenMP runtime. The `ompt_initialize` routine configures the entire scheduler infrastructure, while `ompt_finalize` performs resource cleanup. The `monitor_loop` function implements periodic monitoring and metric analysis. Functions such as `open_perf_for_thread`, `enable_perf`, and `disable_perf` manage hardware counters. The `migrate_to_opposite_node` function performs NUMA migrations, while `cpu_to_numa_node_hwloc` maps processors to NUMA nodes. Finally, the OMPT callback functions provide the integration points required to interact with the OpenMP runtime.

## 18. Expected Behavior

During normal execution, threads are automatically registered as they are created and their hardware counters begin collecting performance information. The scheduler first learns the typical memory access behavior of each thread and then continuously monitors for deviations from this baseline. When excessive remote memory activity is detected, selected threads are migrated to alternative NUMA nodes. After each migration, a stabilization period prevents immediate remigration. This cycle of observation, analysis, and adaptation continues until application termination, allowing the scheduler to dynamically respond to changes in workload behavior and memory access patterns.
